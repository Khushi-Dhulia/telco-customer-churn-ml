# Telco Customer Churn — Machine Learning Engineer Assessment

End-to-end customer churn classification pipeline using scikit-learn and FastAPI.

## What is included

- Brief EDA and data-quality checks
- `TotalCharges` numeric conversion
- Missing-value handling
- Categorical one-hot encoding
- Stratified train/test split
- Logistic Regression baseline
- Random Forest ensemble
- 5-fold cross-validation and hyperparameter tuning
- ROC-AUC, PR-AUC, F1, precision, recall and accuracy
- Serialized preprocessing + model pipeline using `joblib`
- FastAPI inference endpoint
- Sample API test

## Train the models

From the repository root:

```bash
python src/train.py
```

The training script:

1. Loads the CSV.
2. Converts `TotalCharges` to numeric.
3. Removes `customerID` from model features.
4. Performs a stratified train/test split.
5. Builds preprocessing inside an sklearn `Pipeline`.
6. Trains Logistic Regression as the baseline.
7. Tunes Random Forest using 5-fold `GridSearchCV`.
8. Evaluates the models on the held-out test set.
9. Saves the best Random Forest pipeline to `models/churn_model.joblib`.
10. Saves metrics to `reports/metrics.json`.

## Why preprocessing is inside the Pipeline

Preprocessing is fitted only on the relevant training folds during cross-validation. This prevents information from the validation/test data from leaking into preprocessing statistics or category encoding.

The saved artifact contains both preprocessing and the trained estimator, so inference accepts the same raw feature format as training.

### Why accuracy is insufficient

The target is imbalanced, so a model can obtain reasonable accuracy while mostly predicting the majority class. That can still result in poor detection of customers who actually churn.

ROC-AUC measures ranking/separation across thresholds, while PR-AUC focuses more directly on the precision/recall trade-off for the positive class. F1, precision and recall additionally show performance at the selected 0.5 classification threshold.

## Production / engineering considerations

If given two additional days, I would prioritize:

### 1. Model and data monitoring

Add monitoring for feature distributions, prediction probabilities, data drift and model performance once delayed ground-truth churn labels become available.

### 2. Automated training and deployment

Add CI/CD and a reproducible ML workflow covering data validation, training, evaluation, model versioning and deployment. An experiment/model tracking system such as MLflow could be introduced as the project grows.

### 3. Production API hardening

Add Dockerization, structured logging, automated integration tests, model/version metadata, health/readiness checks, configurable classification thresholds and request-level observability.

## Design decisions

- `customerID` is excluded because it is an identifier rather than a predictive customer attribute.
- `TotalCharges` is converted using `pd.to_numeric(..., errors="coerce")`; invalid/blank values are then handled by the numeric imputer.
- `OneHotEncoder(handle_unknown="ignore")` allows the API to safely handle unseen categorical values.
- `class_weight="balanced"` is used to account for the target imbalance.
- Random Forest is tuned using ROC-AUC as the cross-validation scoring metric.
- The final saved artifact is the complete preprocessing + model pipeline rather than only the estimator.
- A 0.5 probability threshold is used for the binary API response; in a real business deployment this threshold should be selected based on the relative cost of false positives and false negatives.

## Reproducibility

A fixed random seed of `42` is used for the train/test split and Random Forest. Exact metric values can still vary with library versions, so the supplied `requirements.txt` should be used for a consistent environment.
